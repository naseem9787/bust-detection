# API Contract — Frontend Integration Guide

**For the frontend developer.** You should not need to read any ML code to
integrate with this backend. Start the service with:

```bash
.venv/Scripts/python.exe -m uvicorn src.production.api:app --reload
```

Interactive docs (auto-generated by FastAPI) are at `http://localhost:8000/docs`
once running — use this contract as the stable reference, the interactive
docs to poke around.

**Read this first:** the system estimates the *probability that a weather
forecast will turn out to be wrong* (a "bust"), not the weather itself. It
is never 100% accurate and makes no guarantees — see every response's
`scientific_framing` / target definitions before building UI copy around it.

---

## `GET /health`

Service liveness + which model versions are actually loaded.

```json
{
  "status": "ok",
  "api_version": "0.1.0",
  "models_loaded": ["rain_v1", "temperature_v1"],
  "timestamp": "2026-09-29T12:00:00Z"
}
```

## `POST /predict`

**Request:**

```json
{
  "init_time": "2021-07-20T00:00:00",
  "lead_day": 5,
  "latitude": 22.5,
  "longitude": 81.0,
  "forecast_precip_mm": 45.2,
  "forecast_temp_c": 28.1,
  "forecast_mslp_hpa": 1003.4,
  "forecast_wind_speed_10m": 4.5
}
```

- `lead_day`: integer 1–10.
- `latitude`: -90..90. `longitude`: accepts either -180..180 or 0..360 (auto-normalized).
- `forecast_wind_speed_10m` is **optional** — omit it and you'll get `rain` results only (`temperature_bust_probability: null`), since the temperature model requires wind.
- `domain_mean_precip_mm`, `domain_mean_temp_c`, `previous_run_forecast_precip_mm`, `previous_run_forecast_temp_c` are all optional refinements with documented fallbacks — skip them for a simpler integration.

**Response (200):**

```json
{
  "prediction": {
    "init_time": "2021-07-20T00:00:00",
    "lead_day": 5,
    "valid_time": "2021-07-25T00:00:00",
    "latitude": 22.5,
    "longitude": 81.0,
    "region": "Madhya Pradesh",
    "in_india_domain": true,
    "forecast_precip_mm": 45.2,
    "forecast_temp_c": 28.1,
    "rain_bust_probability": {
      "raw": 0.0613,
      "calibrated": 0.0613,
      "confidence": 0.9387,
      "risk_level": "low"
    },
    "temperature_bust_probability": {
      "raw": 0.0589,
      "calibrated": 0.0429,
      "confidence": 0.9571,
      "risk_level": "low"
    },
    "model_version": "phase4-production-v1",
    "feature_version": "phase2-feature-schema-v1",
    "calibration_version": "rain=none (raw preserved);temp=isotonic"
  }
}
```

**How to interpret probability vs. confidence:**
- `raw` = the model's direct output. `calibrated` = adjusted so the number
  means what it says (e.g. "of all times we said 30%, it happened ~30% of
  the time") — **always prefer `calibrated` for display**, but both are
  always returned so you can choose.
- `confidence = 1 − calibrated`. This is an **operational reliability
  score**, NOT a formal statistical confidence interval. Higher = the
  forecast is more likely trustworthy.
- `risk_level` is a convenience bucket (`low`/`moderate`/`high`) from the
  thresholds in `/metadata` — don't hard-code 0.25/0.5 in the frontend,
  read them from `/metadata` in case they change.

**Error responses** (structured, never a silent fallback):

| Status | `error` | When |
|---|---|---|
| 422 | (Pydantic validation detail) | bad lead_day/lat/lon/negative precip |
| 422 | `outside_domain` | coordinates are ocean/non-India |

```json
{ "error": "outside_domain", "detail": "(0.0, 65.0) is outside the model's India domain (ocean/distant foreign territory) ..." }
```

## `GET /predictions`

Retrieves the most recently generated **batch** prediction file (produced
by the backend team's `batch_predict` CLI, NOT computed live). Query
params: `init_time`, `lead_day`, `region`, `variable` (`rain`/`temperature`).

If no batch has been run yet, you get a clear 404 — **never fabricated
data:**

```json
{ "error": "no_persisted_predictions", "detail": "No batch predictions have been generated yet. Run `python -m src.production.batch_predict ...` first ..." }
```

## `GET /regions`

```json
[
  { "region": "Rajasthan", "n_grid_points": 17, "known_limitation": null },
  { "region": "Andhra Pradesh", "n_grid_points": 13, "known_limitation": "boundary vintage predates 2014 Telangana split ..." }
]
```

29 regions total. Use this to populate a region picker; `known_limitation`
is non-null only for the 2 regions affected by the boundary-vintage issue.

## `GET /timeseries`

**Historical mode only** (see limitations) — pass a real past `valid_time`
+ location; returns how the rain-bust probability evolved across every
lead day (1–10) that a historical forecast targeted that date.

`GET /timeseries?valid_time=2021-08-01T12:00:00&latitude=24.0&longitude=85.5`

```json
{
  "valid_time": "2021-08-01T12:00:00",
  "latitude": 24.0,
  "longitude": 85.5,
  "trajectory": [
    { "lead_day": 1, "init_time": "2021-07-31 12:00:00", "rain_bust_probability": 0.0011, "rain_confidence": 0.9989 },
    { "lead_day": 9, "init_time": "2021-07-23 12:00:00", "rain_bust_probability": 0.93, "rain_confidence": 0.07 },
    "...": "..."
  ]
}
```

Use this to draw a "how did confidence change as the event approached"
chart — this is the D1→D10 trajectory view.

## `GET /explain`

Real SHAP feature attribution + deterministic human-readable reasons — no
LLM, nothing invented beyond the model's actual features.

`GET /explain?variable=rain&init_time=2021-08-01&lead_day=9&latitude=24.0&longitude=85.5&forecast_precip_mm=92.8&forecast_temp_c=26.1&forecast_mslp_hpa=1001.0`

```json
{
  "variable": "rain",
  "model_version": "v1",
  "base_value": -4.91,
  "raw_probability": 0.9149,
  "top_features": [
    { "feature": "fcst_precip_mm", "value": 92.8, "contribution": 4.80, "direction": "increases_bust_probability" },
    { "feature": "fcst_precip_anomaly_vs_domain_mean", "value": 84.2, "contribution": 1.24, "direction": "increases_bust_probability" }
  ],
  "human_readable_reasons": [
    "The forecast rainfall amount strongly increases the predicted bust probability.",
    "How unusual the rainfall forecast is versus the broader pattern strongly increases the predicted bust probability."
  ]
}
```

`variable=temperature` requires `forecast_wind_speed_10m` (422 without it).
`base_value`/`contribution` are in the model's raw margin (log-odds) space
(standard SHAP convention) — display `human_readable_reasons` directly, or
use `top_features` for a custom "why" panel; don't try to sum
`contribution` values into a percentage without a sigmoid transform.

## Frontend integration checklist

1. **Call `/metadata` once at app startup.** Cache model versions, risk
   thresholds, and the lead-day metric curves for your verification/about page.
2. **For a single point-and-time prediction:** `POST /predict`. Always
   show `calibrated`, keep `raw` available behind an "advanced" toggle if
   you want it.
3. **For confidence/probability display:** use `calibrated` +
   `confidence`; explain confidence as "how reliable this specific
   forecast is estimated to be," never as a formal statistical interval.
4. **For a D1→D10 trajectory at one location/date:** `GET /timeseries`
   (historical data only, for past dates already in our dataset).
5. **For state/region-level views:** `GET /regions` for the list, then
   (once your backend counterpart has run a batch) `GET /predictions?region=...`
   for grid-level rows to aggregate yourself, or ask the backend team for
   region-aggregated fields (`region_max_probability` etc. — see
   `aggregate_region()` in `src/production/aggregation.py`) if you'd rather
   receive them pre-aggregated.
6. **For "why is this risky" panels:** `GET /explain`.
7. **Never call any LightGBM/pandas/training code directly** — everything
   you need is behind these 7 endpoints.
8. **If an endpoint 404s with a structured `error` field**, that means data
   genuinely doesn't exist yet (e.g. no batch run) — show that state
   honestly, don't retry-loop expecting it to appear.
